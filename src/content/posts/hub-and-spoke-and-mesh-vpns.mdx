A VPN gives devices on different networks private addresses on one shared network. Hub-and-spoke and mesh VPNs build the same kind of tunnel. They differ in where the tunnels go.

## What a tunnel does

The laptop sends a normal packet to the phone's private address. The VPN encrypts it and wraps it in a packet the internet can deliver.

```diagram
title "A packet inside a tunnel"
direction right
group outer "Outer packet: 198.51.100.7 to 192.0.2.10 (public, readable)" tone accent {
  inner "Inner packet" detail "10.8.0.2 to 10.8.0.3, encrypted" tone primary
}
```

The other end of the tunnel removes the outer packet, decrypts the inner one, and delivers it.

## Hub and spoke

Every device has one tunnel, to the hub.

```diagram
title "Hub and spoke: every tunnel ends at the hub"
direction right
laptop "Laptop" detail "10.8.0.2" tone primary
phone "Phone" detail "10.8.0.3" tone primary
hub "Hub" detail "10.8.0.1" tone warning
server "Server" detail "10.8.0.9" tone primary
laptop <-> hub
phone <-> hub
hub <-> server
```

The hub keeps the only full table. It maps each private address to a tunnel and to the public address where that tunnel ends.

| Private address | Tunnel | Last seen at |
| --- | --- | --- |
| 10.8.0.2 | Laptop | 198.51.100.7:51820 |
| 10.8.0.3 | Phone | 203.0.113.20:41641 |
| 10.8.0.9 | Server | 192.0.2.44:51820 |

In WireGuard, that table is the hub's list of peers:

```ini
[Interface]
Address = 10.8.0.1/24
ListenPort = 51820

[Peer]
PublicKey = laptop-public-key
AllowedIPs = 10.8.0.2/32

[Peer]
PublicKey = phone-public-key
AllowedIPs = 10.8.0.3/32

[Peer]
PublicKey = server-public-key
AllowedIPs = 10.8.0.9/32
```

A message from the laptop to the phone, and the reply, both pass through the hub:

```sequence
title "Laptop to phone through the hub"
participant laptop "Laptop" tone primary
participant hub "Hub" tone accent
participant phone "Phone" tone primary
laptop -> hub "To 10.8.0.3"
hub -> hub "Look up 10.8.0.3: the phone's tunnel"
hub -> phone "Encrypted again for the phone"
phone --> hub "Reply to 10.8.0.2"
hub -> hub "Look up 10.8.0.2: the laptop's tunnel"
hub --> laptop "Reply"
```

## Mesh

Every device has a tunnel to each peer it talks to. A coordination server tells the devices about each other, but carries none of their traffic. Tailscale works this way.

</div>

Each device keeps its own table, for its own peers. Here is the laptop's, shown the way `tailscale status` lists it (an illustration, not real output):

```text
$ tailscale status
100.101.0.2  laptop  me@  macOS  -
100.101.0.3  phone   me@  iOS    active; direct 203.0.113.20:41641
100.101.0.9  server  me@  linux  active; relay "fra"
```

Most devices sit behind a home router that drops packets nobody asked for. To get through, both devices send to each other at the same time:

```steps
sequence
title "Getting through two home routers"
participant laptop "Laptop" tone primary
participant router_a "Laptop's router"
participant router_b "Phone's router"
participant phone "Phone" tone primary
note laptop..phone "The coordination server gives each side the other's public address"
laptop -> router_a "Send to the phone's public address"
router_a -> router_b "Arrives unasked: dropped"
phone -> router_b "Send to the laptop's public address"
router_b -> router_a "Looks like a reply: let in"
router_a -> laptop "Delivered"
note laptop..phone "Both routers now pass the traffic: a direct path"
step "The coordination server tells each device where the other one is." : 1
step "The laptop sends first. Its router remembers that it sent to the phone." : 2
step "The phone's router has not seen any traffic from the laptop yet, so it drops the packet." : 3
step "The phone sends too. Its router now remembers the laptop." : 4
step "The laptop's router sees what looks like a reply, and lets it in." : 5 6
step "From now on both routers pass the traffic. If this fails, both devices use a relay instead." : 7
```

## Side by side

| | Hub and spoke | Mesh |
| --- | --- | --- |
| Path from laptop to phone | Laptop, hub, phone | Laptop, phone (or a relay) |
| Who holds the table | The hub | Each device, for its own peers |
| What the central server carries | Every packet | No packets: keys, addresses, policy |
| If the central server stops | Nothing connects | Existing connections continue |

The same tunnel and the same kind of table, in two shapes: one table in the middle of a star, or one table on every device of a web.
