Why a Japanese string is not a list of characters: code points, UTF-16 and graphemes, normalization, comparison, word and line breaks, vertical text and ruby. The examples are TypeScript, the demos run this browser's own text APIs, and the last part shows where an app that stores and searches Japanese text needs each idea.

## Characters, code points and code units

A string looks like a list of characters, and for English text that picture rarely fails. For Japanese it fails often, because "character" means at least three different things, and each API counts a different one.

- A **code point** is a number Unicode assigns to one abstract character, written `U+` and hex: `U+3042` is <span lang="ja">あ</span>. The numbers run from `U+0000` to `U+10FFFF`. The first 65,536, up to `U+FFFF`, are the Basic Multilingual Plane, the BMP, and hold almost every character in everyday use.
- A **code unit** is the fixed-size piece an encoding stores: 8 bits in UTF-8, 16 bits in UTF-16. One code point takes one or more code units.
- A **grapheme** is what a reader sees as one character. It can be several code points: <span lang="ja">が</span> can be stored as <span lang="ja">か</span> followed by a separate voiced mark, and a family emoji is three people joined by invisible joiners.

## UTF-8 and UTF-16

An encoding turns code points into bytes. UTF-8 and UTF-16 can both store every code point; they differ in unit size.

- **UTF-8** uses one byte for ASCII, two for most European accented letters, three for the rest of the BMP, kana and nearly all kanji included, and four above it. Files, HTML and network traffic are almost always UTF-8, and `TextEncoder` always produces it.
- **UTF-16** uses one 16-bit unit for every BMP code point. A code point above `U+FFFF` takes two units, a _surrogate pair_: a high surrogate from `D800` to `DBFF` and a low one from `DC00` to `DFFF`, a range reserved so that no real character uses it.

| Character | Code point | UTF-16 units | UTF-8 bytes |
| --- | --- | --- | --- |
| A | `U+0041` | `0041` | `41` |
| é | `U+00E9` | `00E9` | `C3 A9` |
| <span lang="ja">あ</span> | `U+3042` | `3042` | `E3 81 82` |
| <span lang="ja">猫</span> | `U+732B` | `732B` | `E7 8C AB` |
| <span lang="ja">𠮟</span> | `U+20B9F` | `D842 DF9F` | `F0 A0 AE 9F` |

Japanese text is mostly three bytes per character in UTF-8 and two in UTF-16. The four-byte case is not exotic either: <span lang="ja">𠮟</span>, in <span lang="ja">𠮟る</span> (to scold), sits above the BMP, and so do some kanji used in names, such as <span lang="ja">𠮷</span> in <span lang="ja">𠮷野家</span>.

## JavaScript strings are UTF-16

A JavaScript string is a sequence of UTF-16 code units, and most of the string API counts units. `length` is the number of units, indexing returns one unit, and `slice` cuts between units, even in the middle of a surrogate pair.

```ts
const scold = '𠮟る';

scold.length;            // 3: two units for 𠮟, one for る
scold[0];                // '\uD842', half of 𠮟, not a character
[...scold].length;       // 2: the string iterator walks code points
scold.codePointAt(0);    // 0x20B9F
scold.slice(0, 1);       // a lone surrogate
```

A lone surrogate is a legal JavaScript string but not valid Unicode text. `TextEncoder` writes it as `U+FFFD`, the replacement character, and `encodeURIComponent` throws a `URIError`, so a cut in the wrong place shows up later as <span lang="ja">�</span> in a file or as an exception.

The string iterator is the exception: `for…of`, spread and `Array.from` walk code points, so a surrogate pair comes out whole. That fixes the BMP boundary and nothing else, because a code point is still not a grapheme.

## Graphemes, what a reader calls a character

Unicode's text segmentation annex, UAX #29, defines the _extended grapheme cluster_, its best approximation of a user-perceived character that a program can compute: a base character with the marks that combine with it, an emoji sequence joined by zero-width joiners, a flag made of two regional indicators. `Intl.Segmenter` with `granularity: 'grapheme'` implements it.

```ts
const graphemes = new Intl.Segmenter('ja', { granularity: 'grapheme' });

[...graphemes.segment('が')].length; // 1
'が'.length;                          // 2
```

The inspector shows all four counts for any text. Try the decomposed <span lang="ja">が</span>, the emoji, and <span lang="ja">𠮟る</span>: each makes a different pair of counts disagree. Every number comes from this browser: `length`, `Array.from`, `TextEncoder`, `Intl.Segmenter` and `String.prototype.normalize`. A highlighted form is one that changed the grapheme.

The rule of thumb that follows: store and compare strings as strings, count units only to index into them, and use graphemes whenever the count or the cut is something a reader sees, such as a length limit, a cursor step or a truncated title.

## Combining marks and dakuten

A _combining mark_ is a code point that draws onto the character before it instead of taking its own place. Japanese has two: `U+3099`, the combining voiced sound mark (dakuten), and `U+309A`, the combining semi-voiced mark (handakuten). Together with <span lang="ja">か</span> the first draws <span lang="ja">が</span>; with <span lang="ja">は</span> the second draws <span lang="ja">ぱ</span>.

Unicode also has precomposed characters for the common pairs: <span lang="ja">が</span> is `U+304C` by itself. So the same visible <span lang="ja">が</span> has two encodings, one code point or two, and `===` calls them different. The standard calls such sequences _canonically equivalent_: they "represent the same abstract character" and should look and behave the same.

Two more marks look like dakuten and are not combining: `U+309B` <span lang="ja">゛</span> and `U+309C` <span lang="ja">゜</span>, the spacing forms, which take their own place. They turn up in text typed or converted from old systems, such as <span lang="ja">か゛</span>.

## The four normalization forms

Normalization rewrites a string into one chosen form, so that equivalent strings become equal strings. UAX #15 defines four forms on two axes. One axis is the kind of equivalence: _canonical_, for sequences that are the same character, or _compatibility_, a weaker one for characters that "may have distinct visual appearances or behaviors" but stand for the same thing. The other is whether the result is decomposed into base characters and marks, or composed again afterwards.

```ts
'が'.normalize('NFC');  // 'が', U+304C
'が'.normalize('NFD');        // 'が'
'ｶﾞ'.normalize('NFC');        // 'ｶﾞ', unchanged
'ｶﾞ'.normalize('NFKC');       // 'ガ'
```

Every form is idempotent: normalizing twice gives the same result as once. NFC changes nothing a reader can see, which makes it safe to apply to any text before storing it. The K forms change what the text says, and UAX #15 warns that they "must not be blindly applied to arbitrary text".

## Compatibility characters in Japanese text

Japanese text is full of compatibility characters, mostly inherited from older Japanese character sets that had their own half-width and full-width copies of letters. NFKC maps each one onto its plain counterpart:

| Text | After NFKC | What it is |
| --- | --- | --- |
| <span lang="ja">ｶﾞｲﾄﾞ</span> | <span lang="ja">ガイド</span> | Half-width katakana, with a separate half-width voiced mark |
| <span lang="ja">ＡＢＣ１２</span> | <span lang="ja">ABC12</span> | Full-width Latin letters and digits |
| <span lang="ja">㌔</span> | <span lang="ja">キロ</span> | A katakana word squeezed into one square |
| <span lang="ja">㍿</span> | <span lang="ja">株式会社</span> | A square abbreviation of <span lang="ja">株式会社</span>, a kind of company |
| <span lang="ja">①</span> | <span lang="ja">1</span> | A circled number |
| <span lang="ja">ﬁ</span> | <span lang="ja">fi</span> | A Latin ligature |
| <span lang="ja">゛</span> | a space, then `U+3099` | The spacing voiced mark |

That is the right tool for matching a search against a title, and the wrong one for storing the title: a volume called <span lang="ja">①巻</span> would come back as <span lang="ja">1巻</span>. The last row is a surprise worth knowing: NFKC turns the spacing mark into a real space followed by the combining mark, so a naive fold of <span lang="ja">か゛</span> puts a space in the middle of a word.

Hiragana and katakana are not equivalent under any of the four forms. <span lang="ja">ねこ</span> and <span lang="ja">ネコ</span> are different characters to Unicode, as they are to a reader of Japanese, even if a search would want them to match.

## Case folding, and a script with no case

Case folding maps letters to one case so that comparisons ignore it. In JavaScript the usual tool is `toLowerCase()`, and even in English it is not one character to one character: `'ß'.toUpperCase()` is `'SS'`.

Kana and kanji have no case, so case folding does nothing to them. Japanese text still needs folding before a comparison, of other kinds: width (half-width <span lang="ja">ｶ</span> against <span lang="ja">カ</span>), composition (two encodings of <span lang="ja">が</span>), and, where the application decides it should, hiragana against katakana. Full-width Latin letters do have case: `'Ａ'.toLowerCase()` is `'ａ'`, still full-width, so width and case are separate steps.

## Comparing and sorting with a collator

`===` compares code units, and the default `sort()` orders by code units too. A _collator_ compares the way a language sorts. `Intl.Collator` exposes the Unicode Collation Algorithm, which compares at levels: base letters first, then accents, then case and other variants. The `sensitivity` option chooses how many levels count, from `base` (only base letters) to `variant` (everything), which is the default for sorting.

What counts as a base letter, an accent or a variant depends on the locale's rules. With the `ja` locale, in Node, Chromium and WebKit alike, <span lang="ja">か</span> and <span lang="ja">カ</span> compare equal even at `variant`, while the root rules separate them; the voiced <span lang="ja">が</span> differs from <span lang="ja">か</span> at the accent level. The demo runs each comparison in this browser. The collator rows use the `ja` locale, and the last row is the tag-name test from [Tag names](#tag-names).

A collator answers "do these sort as the same?", which is a different question from "are these the same name?". It ignores what its rules ignore and nothing else, and its rules can change with the browser's ICU version. For an equality that a program relies on, such as two tags merging into one, an explicit fold is easier to reason about, and [Tag names](#tag-names) shows one.

## Words without spaces

Japanese writes words with no spaces between them, so `split(' ')` returns a whole sentence as one word. Finding word boundaries takes knowledge of the language: UAX #29 says that reliable word boundaries in Thai, Lao, Chinese or Japanese need dictionary lookup or other mechanisms. Its default rules keep a run of katakana together (rule WB13) and otherwise break around every kanji and hiragana.

`Intl.Segmenter` with `granularity: 'word'` goes further in ICU, the library behind Node and Chromium, which uses a dictionary for Chinese and Japanese words. Each segment comes with `isWordLike`, false for punctuation and spaces. The result is a guess, not a grammar: the classic tongue twister <span lang="ja">すもももももももものうち</span> is mostly the particle <span lang="ja">も</span> and the noun <span lang="ja">もも</span>, and a dictionary split cannot always tell which is which. ICU in Node 24 gets several of them wrong.

The demo calls `new Intl.Segmenter('ja', { granularity })` in this browser. A solid badge is a segment with `isWordLike` set; punctuation and spaces are quiet.

<WordSegmentDemo client:visible />

A segmenter finds where words start and end. It does not say what a word is, what its base form is or how it is read; that is a morphological analyzer's job, a separate and much larger tool.

## Where a Japanese line may break

Line breaking is a separate question from word boundaries, with its own annex, UAX #14. In Japanese a line may break between almost any two characters: ideographs "can ordinarily break before and after and between pairs". The exceptions are the rules Japanese typography calls kinsoku: closing punctuation such as <span lang="ja">。</span> and <span lang="ja">、</span> must not start a line, and opening brackets must not end one.

Small kana such as <span lang="ja">っ</span> and <span lang="ja">ゃ</span>, and the prolonged sound mark <span lang="ja">ー</span>, are a matter of taste. UAX #14 puts them in a class of their own, the conditional Japanese starter, and CSS chooses with the `line-break` property: `strict` keeps them off the start of a line, `normal` lets them start one, and `loose` relaxes the rules further for narrow columns.

## Vertical writing in CSS

Japanese books and manga are set in vertical columns, read top to bottom, with the columns running right to left. CSS writes this with `writing-mode`:

- `horizontal-tb`: horizontal lines stacked top to bottom, the default.
- `vertical-rl`: vertical lines stacked right to left, the Japanese book layout.
- `vertical-lr`: vertical lines stacked left to right, used by Mongolian, among others.

Everything that CSS calls inline or block follows the mode. In `vertical-rl`, `inline-size` is the height of a column, `block-size` is the width of the page, and the start of a line is its top. That is why logical properties, such as `margin-block-start` instead of `margin-top`, keep a layout correct in either mode.

```css
.page {
  writing-mode: vertical-rl;
  text-orientation: mixed;
}

.page .number {
  text-combine-upright: all;
}
```

## Upright and sideways characters

A vertical line still has to place each character, and characters disagree about which way up they go. Kana and kanji stand upright. Latin letters, in a Japanese vertical line, are usually turned on their side, so that a word reads with the head tilted. Unicode records the usual choice for each code point in the `Vertical_Orientation` property of UAX #50: `U` for upright, `R` for rotated, and `Tu` and `Tr` for characters that need a different glyph in vertical text, such as <span lang="ja">。</span>, the small kana, corner brackets and <span lang="ja">ー</span>, which turns into a vertical stroke.

`text-orientation` decides how to apply it. `mixed`, the default, follows the property: kana upright, Latin sideways. `upright` stands every character up, so `OCR` becomes three stacked letters. `sideways` lays the whole line out horizontally and turns it, kana included.

Short runs of digits or Latin letters are often set across the column instead, in the space of one character. Japanese typesetters call it tate-chu-yoko, horizontal in vertical, and CSS writes it as `text-combine-upright: all` on the run. The CSS Writing Modes specification intends it for runs of two to four characters, and squeezes the run if it is wider than the column.

## Ruby for furigana

Furigana are small kana printed beside a kanji to show how it is read, the way a children's book or a manga for younger readers prints them on every hard word. HTML marks them up with ruby: the `ruby` element holds the base text and its annotations, and each `rt` holds one annotation. The `rp` element holds parentheses "to be shown by user agents that don't support ruby annotations"; a browser that supports ruby hides them. The HTML standard's own example:

```html
<ruby>漢<rp>（</rp><rt>かん</rt><rp>）</rp>字<rp>（</rp><rt>じ</rt><rp>）</rp></ruby>
```

In vertical text the readings sit to the right of the column, and in horizontal text above the line. The playground above has a switch that hides every `rt` and `rp` with `display: none`, which is how a reader can turn furigana off.

Ruby text is still text in the document. `textContent` on a ruby element returns the base and the reading run together, so code that copies or searches the text has to leave the readings out on purpose:

```ts
const word = document.createElement('ruby');
word.innerHTML = '鍵<rt>かぎ</rt>';
word.textContent; // '鍵かぎ'
```

[Offsets in a highlight and a quote](#offsets-in-a-highlight-and-a-quote) shows how a reading app removes the readings from what it stores.

## One code point, several glyph styles

Chinese, Japanese and Korean share thousands of characters, and Unicode encodes each one once, even where the three traditions draw it a little differently. The Unicode FAQ puts it plainly: the standard encodes characters, not glyphs, and drawing Japanese text the Japanese way is "a font issue, not a character encoding issue".

So the same code point can look Japanese or Chinese depending on the font. On the web the font follows the language: the `lang` attribute tells the browser which language an element is in, and CSS can match it with `:lang(ja)` to choose a Japanese font. Text with no `lang`, or the wrong one, is drawn in whatever font the page's styles and the browser's fallback list produce, which can be a Chinese one.

## Unicode in a reading app

The same ideas decide how an app that stores and searches Japanese text should treat it. Each part below is one place where text enters, is compared, is cut or is shown, with the code that handles it. The examples come from a reading app for books and manga, where a book carries its own language.

### NFC where a file name enters the app

A book's title in a reading app usually starts as a file or folder name, and a file name is the one piece of text whose normalization nobody controls. I found a Korean title, read from a folder name on a Mac, that came through decomposed: its first syllable, <span lang="ko">나</span>, was the two jamo `U+1102 U+1161` instead of the one code point `U+B098` a keyboard types. It looked identical and matched nothing.

So the adapter that turns a browser `File` into the app's own values composes the name with NFC on the way in:

```ts
function canonical(text: string): string {
  return text.normalize('NFC');
}

function entryName(file: File): string {
  const named = file.webkitRelativePath.length > 0 ? file.webkitRelativePath : file.name;

  return canonical(named);
}
```

The upload's name and the title suggested from a file name are normalized the same way. NFC is safe for every language, because it only chooses between canonically equivalent spellings, so the adapter does not need to know the book's language, which it could not know from a file name anyway.

The boundary uses NFC and never NFKC. A test checks that a file named <span lang="ja">①巻 ﬁnale Ａ.cbz</span> keeps all three compatibility characters.

### Titles in book matching

When an upload is matched against books the app already holds, removed or unreadable, the last step of the matching compares titles. Both sides go through the same function first:

```ts
const UNTITLED_BOOK = 'Untitled';

function matchableTitle(title: string): string | null {
  const normalised = title.normalize('NFC').trim();
  if (normalised.length === 0 || normalised === UNTITLED_BOOK) return null;
  return normalised;
}
```

NFC, then trimming, and nothing more: no case folding and no width folding. A title is an identity key here, and a looser comparison would join two different books whose titles differ only in width or case. An empty title and the placeholder for an untitled book never match anything.

### Folding for search

Search is where an app folds hard. The title search, the search over saved passages, the tag filter and the quick find all fold the text and the query the same way before an ordinary `indexOf`. The fold works one grapheme cluster at a time:

```ts
const GRAPHEMES = new Intl.Segmenter(undefined, { granularity: 'grapheme' });

function clustersOf(text: string): readonly string[] {
  return [...GRAPHEMES.segment(text)].map((found) => found.segment);
}

function widthFolded(character: string): string {
  return STANDALONE_MARKS.get(character) ?? character.normalize('NFKC');
}

function kanaFolded(character: string): string {
  const code = character.codePointAt(0);
  if (code === undefined || code < KATAKANA_FIRST || code > KATAKANA_LAST) return character;

  return String.fromCodePoint(code - KANA_SHIFT);
}
```

- **Width and compatibility.** Each cluster goes through NFKC, so <span lang="ja">ｶﾞ</span>, <span lang="ja">ガ</span> and the decomposed <span lang="ja">カ</span> plus `U+3099` all become <span lang="ja">ガ</span>, and <span lang="ja">ＯＣＲ</span> becomes `OCR`. The spacing marks <span lang="ja">゛</span> and <span lang="ja">゜</span> are first swapped for the combining ones, because NFKC would turn them into a space and a mark.
- **Case.** `toLowerCase()` on the result.
- **Kana.** Katakana from `U+30A1` to `U+30F6` shifts down by `0x60` onto the matching hiragana. The range stops at <span lang="ja">ヶ</span>. Past it are <span lang="ja">ヷ</span> to <span lang="ja">ヺ</span>, which have no hiragana, the middle dot, and <span lang="ja">ー</span>, which the shift would turn into `U+309C`, the spacing semi-voiced mark.
- **Voiced marks.** A combining mark left over after a fold is composed onto the kana before it with NFC, when a precomposed character exists.

```ts
for (const character of clustersOf(text)) {
  for (const part of widthFolded(character).toLowerCase()) {
    const shifted = kanaFolded(part);
    const composed = composedWith(folded.slice(-1), shifted);

    if (composed !== '') {
      folded = folded.slice(0, -1) + composed;
      continue;
    }

    folded += shifted;
    for (let unit = 0; unit < shifted.length; unit += 1) origins.push(offset);
  }

  offset += character.length;
}
```

The fold changes lengths in both directions: <span lang="ja">㌔</span> becomes two characters and <span lang="ja">ｶﾞ</span> becomes one. A match found in the folded text is a position in the folded text, and highlighting it in the original needs a map back. That is `origins`: for each UTF-16 unit of folded output, the offset of the cluster in the original that produced it. Units rather than code points, because `indexOf` returns a unit index.

The demo runs the fold and the match, and draws the highlight on the original text from the offsets the fold keeps.

Grapheme clusters are what made the Korean title above searchable. An earlier version folded one code point at a time, and NFKC on a lone jamo cannot compose it with the next one. A decomposed syllable is one cluster, so NFKC on the cluster composes it, and the cluster still has one offset in the original string for the highlight.

### Tag names

A tag's name is cleaned once, when it is created or renamed: trimmed, composed with NFC, and every run of whitespace inside it collapsed to one space. That cleaned name is what is stored and shown.

```ts
function tagName(raw: string): string {
  return raw.trim().normalize('NFC').replaceAll(INNER_SPACE, ' ');
}
```

Whether two names are the same tag is a stricter question, because a duplicate is confusing. The answer is the search fold applied to both cleaned names:

```ts
function sameTagName(left: string, right: string): boolean {
  return foldForSearch(tagName(left)).text === foldForSearch(tagName(right)).text;
}
```

So `Vocab` and `vocab` are one tag, and so are <span lang="ja">ﾀｸﾞ</span>, <span lang="ja">タグ</span> and <span lang="ja">たぐ</span>. Creating or renaming a tag to a name that is already taken in this sense is refused, and an import merges tags by the same test. The last row of the [same-or-not demo](#comparing-and-sorting-with-a-collator) runs it.

### Natural order for file names

Page images inside an archive or a folder are ordered by name, and the order becomes the page index. Code-unit order puts `page10` before `page2`, so the app sorts with a numeric collator:

```ts
const collator = new Intl.Collator(undefined, { numeric: true, sensitivity: 'base' });

function compareNatural(a: string, b: string): number {
  const byCollator = collator.compare(a, b);
  if (byCollator !== 0) return byCollator;
  if (a === b) return 0;
  return a < b ? -1 : 1;
}
```

`sensitivity: 'base'` ignores case, so `A.jpg` and `a.jpg` compare equal, and numeric collation calls `page02` and `page2` equal too. An archive can hold both, and a sort that returns 0 for two different names leaves their order to the input. The fallback to plain code-unit order makes the order total, so the same files always get the same page numbers.

The first list is `compareNatural`; the second is the default `sort()`, by UTF-16 code units.

### Offsets in a highlight and a quote

A highlight taken in an EPUB reader stores two things to find its passage again: an EPUB CFI and a text quote. The CFI's character offset counts UTF-16 code units, the same units as a DOM `Range` offset and a JavaScript `length`.

The quote is the selected text as `exact`, with up to 32 characters before and after it as `prefix` and `suffix`. The 32 are counted with `Array.from`, so in code points, and a cut never falls inside a surrogate pair:

```ts
function keptBefore(text: string): string {
  const runes = Array.from(text);
  return runes.slice(Math.max(0, runes.length - QUOTE_CONTEXT_CHARS)).join('');
}

function keptAfter(text: string): string {
  return Array.from(text).slice(0, QUOTE_CONTEXT_CHARS).join('');
}
```

All three strings leave the furigana out. The app clones the selected range, removes its `rt` and `rp` elements, and reads the text that is left:

```ts
function withoutReadings(fragment: DocumentFragment): string {
  for (const reading of fragment.querySelectorAll(RUBY_READINGS)) reading.remove();

  return fragment.textContent ?? '';
}
```

Finding the quote later searches the chapter's text with the same elements skipped, and compares code units with `indexOf`. Neither side is normalized; both come from the same book's markup.

### Furigana in the text settings

The text settings of a reading app include a switch labeled **Furigana / Hanja**, on by default. The label names both because Korean books can print readings over hanja with the same ruby markup, and the stored setting has a language-neutral name, `showPhoneticReadings`.

Turning it off adds one rule to the styles the app injects into each chapter, after the book's own stylesheets:

```ts
const THE_READINGS_ARE_PUT_AWAY = `
  rt, rp {
    display: none !important;
  }
`;
```

With `!important`, no rule in the book's own stylesheets can show the readings again. The readings stay in the document, so turning the switch back on needs no reload. Whatever the setting, `rt` is drawn at `0.6em`.

### The text OCR returns

A Japanese OCR model such as manga-ocr has a tokenizer that works one character at a time and puts a space between every pair when it turns token ids back into text: <span lang="ja">こ ん に ち は</span>. Before the worker posts the text back, `jaOcrText`, a function in a file beside the manga-ocr worker, removes every run of whitespace:

```ts
function jaOcrText(decoded: string): string {
  return decoded.replace(/\s+/gu, '');
}
```

That is the only change. manga-ocr's own Python `post_process` also replaces <span lang="ja">…</span> and runs of <span lang="ja">・</span> with dots, then widens ASCII and digits to full width with `jaconv.h2z`; the app keeps what the model produced. Width matters only for matching, and the search fold already handles it, so a half-width digit in a saved passage is still found by a full-width query.

The strip runs in the Japanese worker only. Korean and English are read by a PaddleOCR model, whose words are separated by real spaces; its worker keeps them and joins the lines it reads with a newline. Either way, the recognizer adapter trims the text before it is stored.

### The language on each element

Every book has a language, Japanese, Korean or English, chosen per book. Wherever the app shows a book's own text, a title, a saved passage, a chapter name or the reader's view, the element gets `lang` set to that language. The base stylesheet gives each language its own font through `:lang()`:

```css
:where([lang]:lang(ja)) {
  --font-body: var(--font-ja);
  --font-display: var(--font-ja);
  font-family: var(--font-ja);
}
```

`--font-ja` resolves to Hiragino Mincho ProN, then Yu Mincho, then the system serif, so a kanji in a Japanese title is drawn with a Japanese font even in an English interface, whose document is `lang="en"`.

## Rules for text in a reading app

- Compose text with NFC where it enters the app from outside, and store it composed. Never store the result of NFKC.
- Compare names and search text through the fold, which folds by grapheme cluster. Compare identity keys, such as titles in matching, with NFC and trimming only.
- Keep an offset that indexes a string in UTF-16 units, and count context or a visible length without splitting a surrogate pair.
- Leave `rt` and `rp` out of any text that is stored or searched.
- Undo only what decoding added to OCR output, and leave what the model read alone.
- Set `lang` from the book's language on every element that shows its text.
