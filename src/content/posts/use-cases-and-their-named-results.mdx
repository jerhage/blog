## One use case per operation

A use case is one thing the app does: search cards, save a deck. One way to think about it is a service layer. It holds the business rules of one operation, and it talks to the data access layer through ports.

Each use case gets its own file, even when it only wraps one port call. It is stateless: the ports it needs come in as an argument.

## Each one names its outcomes

The result is a union discriminated on `type`. The success variant names what it holds. Every expected outcome is a variant beside it.

```ts
type SaveDeckResult =
  | { type: 'saved'; deck: Deck }
  | { type: 'deck-too-large'; limit: number }
  | { type: 'storage-unavailable' };
```

```diagram
title "Three outcomes of saving a deck"
direction right
save "saveDeck" tone primary
saved "saved" detail "holds the deck" tone success
large "deck-too-large" detail "expected" tone warning
storage "storage-unavailable" detail "expected" tone warning
save -> saved
save -> large
save -> storage
```

An expected outcome is one the caller can do something about: tell the person the deck is too big, or that a private window blocks storage.

## Expected or unexpected

| Failure | Where it goes |
| --- | --- |
| Deck too large | a variant of the result |
| Storage blocked in a private window | a variant of the result |
| A card row with no image, a bug, a broken store | thrown, caught at a boundary |

One question sorts them: can the caller do something meaningful with it? If yes, it is a variant. If no, it throws to a boundary that logs it and shows a failure. A thrown error keeps its meaning of "something nobody planned for". [Expected and unexpected failures](/posts/expected-and-unexpected-failures/) follows both routes through the layers.

## Passing outcomes on

`saveDeck` shows both jobs. It applies a business rule, the deck limit, and then stores the deck through its port. When the port answers with a failure, the use case narrows instead of matching.

```ts
async function saveDeck(
  draft: DeckDraft,
  { clock, deckSaver, idGenerator }: SaveDeckCapabilities,
): Promise<SaveDeckResult> {
  if (draft.cards.length > DECK_LIMIT) {
    return { type: 'deck-too-large', limit: DECK_LIMIT };
  }

  const deck = buildDeck(draft, idGenerator.deckId(), clock.now());
  const stored = await deckSaver.put(deck);
  if (stored.type !== 'success') return stored;

  return { type: 'saved', deck: stored.deck };
}
```

After the `if`, `stored` is every variant of the port's answer except success. That remainder must fit `SaveDeckResult`. If the port gains a variant the use case does not name, the `return` stops compiling until it does.

## Deciding what an outcome means

Where each outcome gets a text or a recovery, the caller matches on `type`, and the match is exhaustive.

```tsx
function saveMessage(result: SaveDeckResult) {
  return match(result)
    .with({ type: 'saved' }, () => 'Deck saved')
    .with({ type: 'deck-too-large' }, ({ limit }) => `At most ${limit} cards`)
    .with({ type: 'storage-unavailable' }, () => 'Storage is blocked')
    .exhaustive();
}
```

A fourth outcome fails to compile in every caller that matches, so a new outcome cannot be forgotten. Without `.exhaustive()` the new case would fall through to a default branch and show nothing, or the wrong text, until someone noticed.

## Why not one `Result<T, E>`

A generic result is one type for every operation: an `ok` flag, a value, and an error.

| | Generic `Result<T, E>` | Named union per use case |
| --- | --- | --- |
| Return type | the same everywhere | one per operation |
| Passing a failure on | one line | one line, by narrowing |
| The success | always called `value` | named for what it holds |
| Several legitimate outcomes | all but one are squeezed onto the error side | each is a peer |

`ok` has two values. An operation with three legitimate outcomes puts two of them beside failures nobody expected, and the type cannot tell the kinds apart. A catch-all "storage failed" variant also spreads into every domain's error type. A named union lists only what that operation can answer.
