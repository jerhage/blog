## Two kinds of state

A deck builder screen holds two different things. Boundary state is everything about talking to storage: waiting, failing, retrying, paging. UI state is everything else: the filter text, the selected card, an open sheet.

```diagram
title "Two kinds of state, two owners"
direction right
group boundary "Boundary state" tone primary {
  data "Data component" detail "loading, failed, ready"
}
group ui "UI state" tone accent {
  hook "Hook" detail "filter, selection, open sheet"
}
```

| | Boundary state | UI state |
| --- | --- | --- |
| Example | the card search is loading | the filter text |
| Timing | asynchronous, can go stale | synchronous, local |
| Owner | a data component | a hook, or the component itself |

## A read data component owns one read

`CardsData` runs the card search, draws the loading and failure states itself, and gives its children ready cards only.

```diagram
title "A read data component"
direction down
cards "CardsData" detail "owns the read" tone primary
spinner "Loading view" detail "draws itself"
failure "Failure view" detail "draws itself"
grid "CardGrid" detail "ready cards only" tone success
cards -> spinner "loading"
cards -> failure "failed"
cards -> grid "ready"
```

Its state is a union, so the component cannot forget a case. The paged version nests the second lifecycle inside `success`, because "loading more" cannot exist before anything has loaded.

```ts
type ReadState<Result> =
  | { type: 'loading' }
  | { type: 'failed'; error: unknown }
  | Result;

type PagedReadState<Item> =
  | { type: 'loading' }
  | { type: 'failed'; error: unknown }
  | { type: 'success'; items: Item[]; hasMore: boolean; paging: PagingState };

type PagingState =
  | { type: 'idle' }
  | { type: 'loadingMore' }
  | { type: 'failed'; message: string };
```

The data component takes the port its read needs, `CardSearcher`, and the query factory calls the use case with it. It matches the state with `match(...).exhaustive()`. It handles every variant itself, and a variant added later fails to compile here and nowhere else.

```tsx
type CardsDataProps = {
  cardSearcher: CardSearcher;
  query: CardQuery;
  children: (ready: { items: Card[]; loadMore: () => void }) => ReactNode;
};

function CardsData({ cardSearcher, query, children }: CardsDataProps) {
  const { state, loadMore, reload } = usePagedReadState(
    searchCardsQuery(query, { cardSearcher }),
    CARD_PAGING,
  );

  return match(state)
    .with({ type: 'loading' }, () => <Spinner />)
    .with({ type: 'failed' }, () => <ErrorState onRetry={reload} />)
    .with({ type: 'success' }, ({ items }) => children({ items, loadMore }))
    .exhaustive();
}
```

The children never see these. A child that received a loading flag would have to decide what to draw while loading, and every screen would decide differently.

```tsx
<CardsData cardSearcher={cards.cardRepository} query={query}>
  {({ items, loadMore }) => <CardGrid cards={items} onEnd={loadMore} />}
</CardsData>
```

The page takes `cards.cardRepository` from the container. It satisfies `CardSearcher`, so the page passes it straight in.

## A hook owns UI state for one concern

A hook is a `useX()` function. It returns the value and a named setter for each change. It never reads data and never calls a use case, and it changes state in callbacks, not in effects.

```ts
function useCardFilter() {
  const [text, setText] = useState('');
  const [pitch, setPitch] = useState<Pitch | 'any'>('any');

  const query: CardQuery = { text, pitch };

  return { query, setText, setPitch };
}
```

The data component takes the hook's `query` as an input to its read, and never owns the filter. Otherwise the text field would have to reach up into whatever runs the search.

A rule that combines data and state is a pure function: `visibleCards(cards, filter)` takes both and returns a list.

## Pure components

A pure component takes props and reports what happened through callbacks. It never sees loading, failure or the cache.

```tsx
function CardGrid({ cards, onPick }: CardGridProps) {
  return (
    <ul>
      {cards.map((card) => (
        <li key={card.id}>
          <button onClick={() => onPick(card)}>{card.name}</button>
        </li>
      ))}
    </ul>
  );
}
```

```diagram
title "Props in, callbacks out"
direction right
parent "Parent" detail "owns state" tone primary
pure "CardGrid" detail "pure component" tone success
parent -> pure "props"
pure -> parent "callbacks"
```

It can be written and tested as if the data always exists, because for this component it always does.

## A write owns its state too

Saving a deck is a write. Its owner, a write data component over `useWriteState`, holds the in-flight state and the outcome of the use case. What reaches the button is a described action, not two booleans.

```ts
type SaveDeckAction = {
  label: string;
  availability: 'busy' | 'ready';
  message: string | null;
  save(): void;
};
```

```tsx
function DeckSaveData({ clock, deckSaver, idGenerator, draft, children }: DeckSaveDataProps) {
  const { state, submit } = useWriteState(saveDeckMutation({ clock, deckSaver, idGenerator }));

  return children({
    label: saveLabel(state),
    availability: state.type === 'saving' ? 'busy' : 'ready',
    message: saveMessage(state),
    save: () => submit(draft),
  });
}
```

A `busy` flag and an `enabled` flag allow four combinations, and one of them, busy and enabled at once, means nothing. One stored value cannot hold it. The button derives its spinner and its disabled state from `availability`.

## Where each part stops

| Part | Holds | Never |
| --- | --- | --- |
| Read data component | one read: loading, failed, ready | UI choices |
| Write owner | one write and its outcome | a read |
| Hook | UI state for one concern | a read, a use case call |
| Pure component | nothing | lifecycle |

A read data component draws in place of its children only when it cannot produce what they need. A write can always draw its controls, so it draws them and only describes their state.
