## One question sorts every failure

The test is one question: can the caller do something meaningful with this? If yes, it's expected. If no, it's unexpected.

```diagram
title "The one question"
direction down
failure "A failure" tone warning
question "Can the caller do something meaningful with this?" tone primary
expected "Expected" detail "a variant of the return type" tone success
unexpected "Unexpected" detail "thrown to a boundary" tone danger
failure -> question
question -> expected "yes"
question -> unexpected "no"
```

What I want is for a thrown exception to keep its meaning of "something I didn't plan for". TypeScript does not put a throw in a signature, so `getCard(): Card` may really mean "a card, or anything thrown". Answering the question first keeps a throw rare and a variant honest.

| Expected | Unexpected |
| --- | --- |
| Card not found | A card row with no image |
| Storage blocked in a private window | A malformed response, a network error |
| Deck too large | A broken store, a bug |
| Unauthorized | A status code nobody listed |

## Two routes up the layers

An expected failure is a named variant of the result, so it travels up as data. An unexpected one throws past the layers in between and lands in one boundary.

```diagram
title "Two routes for a failure"
direction down
adapter "HTTP card repository" detail "classifies the response" tone accent
usecase "findCard use case" detail "names the outcome" tone primary
data "Card data component" detail "matches every variant" tone primary
pure "Card view" detail "ready card only" tone success
boundary "Failure boundary" detail "logs once, shows a failure" tone danger
adapter -> usecase "expected: an answer"
usecase -> data "expected: a variant"
data -> pure "found: the card"
adapter -> boundary "unexpected: throws"
```

## The adapter classifies

The adapter turns the few outcomes the screen can use into answers and sends everything else to the default: not OK means unexpected. It never lists every status code. Here it implements the `CardFinder` port, which answers a missing card with `null`.

```ts
class HttpCardRepository implements CardFinder {
  async get(id: CardId, options?: ReadOptions): Promise<Card | null> {
    let body: unknown;
    try {
      body = await fetchJson(`/cards/${id}`, options);
    } catch (error) {
      if (error instanceof HttpError && error.status === 404) return null;
      throw error;
    }

    return parseCard(body);
  }
}
```

`fetchJson` is one shared helper: it throws an `HttpError` for any response that is not OK, and a network failure rejects as well. The adapter catches only the 404, because the screen has an answer for it, and rethrows everything else. A 500, a network error, or a code added next year stays a throw: the query retries it and the read ends in its `failed` state.

## Validate where data arrives

`parseCard` throws on a response that is not a card. Past the adapter the types can be trusted, so no layer above checks again.

## The use case names the outcome

The use case turns the port's `null` into a named variant.

```ts
type FindCardResult = { type: 'success'; card: Card } | { type: 'not-found' };

async function findCard(
  id: CardId,
  { cardFinder }: FindCardCapabilities,
  options?: ReadOptions,
): Promise<FindCardResult> {
  const card = await cardFinder.get(id, options);
  return card ? { type: 'success', card } : { type: 'not-found' };
}
```

## The data component draws each one

The data component takes the `CardFinder` port, and its query factory calls `findCard` with it. It matches every variant, so each expected failure gets a view of its own. The unexpected `failed` state is the one generic branch.

```tsx
function CardData({ cardFinder, id, children }: CardDataProps) {
  const { state, reload } = useReadState(cardQuery(id, { cardFinder }));

  return match(state)
    .with({ type: 'loading' }, () => <Spinner />)
    .with({ type: 'success' }, ({ card }) => children(card))
    .with({ type: 'not-found' }, () => <Notice text="No card has this id." />)
    .with({ type: 'failed' }, () => <ErrorState onRetry={reload} />)
    .exhaustive();
}
```

An expected failure resolves the query, so retries and caching treat it as an answer. Only a throw rejects, and one hook on the query client logs every rejection in one place.

## What it buys in maintenance

A new expected outcome is a new variant. The compiler then lists every `match` that has no branch for it.

```diagram
title "A new variant finds every match"
direction down
variant "rate-limited" detail "added to FindCardResult" tone warning
data "Card data component" detail "fails to compile" tone accent
page "Card page" detail "fails to compile" tone accent
variant -> data
variant -> page
```

Unexpected failures need no such list: they all end at the same boundary, and one function logs them, so a new kind of bug needs no new handling.

## The difference in short

Expected failures are the ones a caller can do something meaningful with, so they are typed and each screen explains them. Unexpected failures are the rest, so they throw to one place that logs them and shows a failure. A throw always means "something I didn't plan for".
