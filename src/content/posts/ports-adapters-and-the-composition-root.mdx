## A port is named for the need, an adapter for the mechanism

The `cards` domain needs to find cards. That need is the port, `CardCatalog`. The adapter is named for what it crosses to: an HTTP card API, a local fixture file.

```diagram
title "One port, two adapters"
direction down
port "CardCatalog" detail "port, declared by the domain" tone primary
http "HttpCardCatalog" detail "adapter: card API" tone accent
fixture "FixtureCardCatalog" detail "adapter: local JSON file" tone accent
http -> port "implements"
fixture -> port "implements"
```

| Port (named for the need) | Adapter (named for the mechanism) |
| --- | --- |
| `CardCatalog` | `HttpCardCatalog`, `FixtureCardCatalog` |
| `DeckRepository` | `IndexedDbDeckRepository` |
| `Clock` | `SystemClock`, `FixedClock` |

An adapter is named for the store or device it crosses to, not the library it uses on the way. If the decks live in IndexedDB and a helper library wraps it, the adapter is still `IndexedDbDeckRepository`. Swapping the helper renames nothing.

## Swapping an adapter

The use case sees only the port, so a test hands it the fixture adapter and the app hands it the HTTP one.

```ts
type CardCatalog = {
  search(query: CardQuery, options: ReadOptions): Promise<SearchCardsResult>;
};

const searchCards = (deps: { catalog: CardCatalog }, query: CardQuery) =>
  deps.catalog.search(query, {});

const inTest = { catalog: new FixtureCardCatalog(fixtureCards) };
const inApp = { catalog: new HttpCardCatalog(fetch) };
```

An adapter catches a failure only to translate it into an answer the caller can act on, such as a blocked store. Anything else throws to a boundary.

## Time and ids are ports too

The clock, an id generator and a random source reach outside the program like storage does. Each is a port, so a test can fix them.

```ts
type SaveDeckDeps = {
  decks: DeckRepository;
  now: () => number;
  newId: () => DeckId;
};

const saveDeck = (deps: SaveDeckDeps, draft: DeckDraft) => {
  const deck = { ...draft, id: deps.newId(), savedAt: deps.now() };
  return deps.decks.put(deck);
};
```

With a fixed clock and ids handed out in sequence, a test can assert on the exact deck it gets back.

## The composition root builds every adapter

One file creates the adapters and binds them into use cases. No other module imports an adapter.

```diagram
title "Only the composition root touches adapters"
direction down
root "Composition root" detail "builds adapters, binds use cases" tone warning
adapters "Adapters" detail "HTTP, IndexedDB, fixture" tone accent
usecases "Use cases" detail "receive ports" tone primary
screens "Pages and UI" detail "receive use cases" tone success
root -> adapters "builds"
root -> usecases "binds ports"
root -> screens "container"
```

```ts
const catalog = new HttpCardCatalog(fetch);
const decks = new IndexedDbDeckRepository(database);
const saveDeckDeps = { decks, now: Date.now, newId };

const container = {
  cards: { searchCards: (query) => searchCards({ catalog }, query) },
  decks: { saveDeck: (draft) => saveDeck(saveDeckDeps, draft) },
};
```

Pages receive the container through React context, so a component asks for it and never imports an adapter.

```tsx
const ContainerContext = createContext(container);

const useContainer = () => useContext(ContainerContext);
```

## What the container exposes

There are two ways to shape it.

| | Exposes use cases | Exposes capabilities (the ports) |
| --- | --- | --- |
| A screen can call a port | no, the type has none | yes, a convention has to stop it |
| Where a use case's dependencies are built | in the root | where the use case is called |
| Size of the root | grows with every use case | grows with the adapters |

Exposing use cases makes "a screen never reaches a port" a type error. Exposing capabilities keeps the root small and leaves that rule to review.

## A heavy adapter loads on demand

When the right adapter depends on a property of the data, the root matches on it and loads each adapter with a dynamic import. A screen that never needs one never downloads it.

```ts
async function loadBitmap(): Promise<Thumbnailer> {
  const { create } = await import('./adapters/bitmap-thumbnailer');
  return create();
}

const loadThumbnailer = (kind: ImageKind) =>
  match(kind)
    .with('bitmap', loadBitmap)
    .with('vector', loadVector)
    .exhaustive();
```

The exhaustive match fails to compile when a new kind has no adapter. One thing no compiler catches: turning the dynamic import into a static one still compiles and passes every rule. Only the bundle grows.
