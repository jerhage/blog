## A port is named for the need, an adapter for the mechanism

The `cards` domain needs to search cards. That need is the port, `CardSearcher`. The adapter is named for what it crosses to: an HTTP card API, a local fixture file.

```diagram

direction down
port "CardSearcher" detail "port, declared by the domain" tone primary
http "HttpCardRepository" detail "adapter: card API" tone accent
fixture "FixtureCardRepository" detail "adapter: local JSON file" tone accent
http -> port "implements"
fixture -> port "implements"
```

| Port (named for the need) | Adapter (named for the mechanism) |
| --- | --- |
| `CardSearcher`, `CardFinder` | `HttpCardRepository`, `FixtureCardRepository` |
| `DeckFinder`, `DeckSaver` | `IndexedDbDeckRepository` |
| `Clock` | `SystemClock`, `FixedClock` |

## A repository satisfies several small ports

Each port holds one need. A repository groups the ports of one kind of data, and one adapter implements it.

```ts
type CardFinder = {
  get(id: CardId, options?: ReadOptions): Promise<Card | null>;
};

type CardSearcher = {
  search(query: CardQuery, page: PageCursor, options?: ReadOptions): Promise<Page<Card>>;
};

type CardRepository = CardFinder & CardSearcher;
```

A use case or a data component asks for the one port it needs. Anything that holds a `CardRepository` can pass it there, because it satisfies every port in the group.

An adapter is named for the store or device it crosses to, not the library it uses on the way. If the decks live in IndexedDB and a helper library wraps it, the adapter is still `IndexedDbDeckRepository`. Swapping the helper renames nothing.

[Narrow capabilities instead of one repository](/posts/narrow-capabilities-instead-of-one-repository/) explains why the ports stay narrow.

## Swapping an adapter

The use case sees only the port, so a test hands it the fixture adapter and the app hands it the HTTP one.

```ts
async function searchCards(
  query: CardQuery,
  page: PageCursor,
  { cardSearcher }: SearchCardsCapabilities,
  options?: ReadOptions,
): Promise<SearchCardsResult> {
  return { type: 'success', page: await cardSearcher.search(query, page, options) };
}

const inTest = { cardSearcher: new FixtureCardRepository(fixtureCards) };
const inApp = { cardSearcher: new HttpCardRepository(fetch) };
```

An adapter catches a failure only to translate it into an answer the caller can act on, such as a blocked store. Anything else throws to a boundary.

## Time and ids are ports too

The clock, an id generator and a random source reach outside the program like storage does. Each is a port, so a test can fix them.

```ts
type SaveDeckCapabilities = {
  clock: Clock;
  deckSaver: DeckSaver;
  idGenerator: IdGenerator;
};

function saveDeck(draft: DeckDraft, { clock, deckSaver, idGenerator }: SaveDeckCapabilities) {
  const deck = { ...draft, id: idGenerator.deckId(), savedAt: clock.now() };
  return deckSaver.put(deck);
}
```

With a fixed clock and ids handed out in sequence, a test can assert on the exact deck it gets back.

## The composition root builds every adapter

One file creates the adapters and puts them in a container. No other module imports an adapter.

```diagram
title "Only the composition root touches adapters"
direction down
root "Composition root" detail "builds adapters" tone warning
adapters "Repositories" detail "HTTP, IndexedDB, fixture" tone accent
screens "Pages" detail "take repositories from the container" tone success
data "Data components" detail "take one port each" tone primary
usecases "Use cases" detail "called with ports by query factories" tone primary
root -> adapters "builds"
adapters -> screens "container"
screens -> data "a repository as a port"
data -> usecases "through a query factory"
```

```ts
const container = {
  cards: { cardRepository: new HttpCardRepository(fetch) },
  decks: { deckRepository: new IndexedDbDeckRepository(database) },
  notes: { noteRepository: new IndexedDbNoteRepository(database) },
  clock: new SystemClock(),
  idGenerator: new CryptoIdGenerator(),
};
```

Pages receive the container through React context, so a component asks for it and never imports an adapter.

```tsx
const ContainerContext = createContext(container);

const useContainer = () => useContext(ContainerContext);
```

```tsx
function DeckBuilderPage() {
  const { cards } = useContainer();
  const filter = useCardFilter();

  return (
    <CardsData cardSearcher={cards.cardRepository} query={filter.query}>
      {({ items, loadMore }) => <CardGrid cards={items} onEnd={loadMore} />}
    </CardsData>
  );
}
```

The page passes `cards.cardRepository` where `CardsData` asks for a `CardSearcher`. `CardsData` never learns which adapter it holds.

## What the container exposes

The container holds repositories and other adapters. It holds no use cases. A query factory or a mutation calls a use case with the ports it needs, at the place where it is called.

## A heavy adapter loads on demand

When the right adapter depends on a property of the data, the root matches on it and loads each adapter with a dynamic import. A screen that never needs one never downloads it.

```ts
async function loadBitmap(): Promise<Thumbnailer> {
  const { create } = await import('./adapters/bitmap-thumbnailer');
  return create();
}

const loadThumbnailer = (kind: ImageKind) =>
  match(kind)
    .with('bitmap', loadBitmap)
    .with('vector', loadVector)
    .exhaustive();
```

The exhaustive match fails to compile when a new kind has no adapter. One thing no compiler catches: turning the dynamic import into a static one still compiles and passes every rule. Only the bundle grows.
